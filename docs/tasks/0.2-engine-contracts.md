# 任务 0.2：引擎契约（负责：Opus；Fable 评审）

## 目标

定义 `packages/engine` 的公共类型契约、`packages/policy-data` 的参数与 fixture（黄金案例）格式，并给两个来自官方文件的示例 fixture。不实现任何规则逻辑。目的是让 Phase 1 三路并行（Opus 写规则、astra 写 UI、sol 写 fixtures 工具链）有共同接口。

## 背景

- 先读 `AGENTS.md`（含不过度工程化规则），再读 `docs/00-project-analysis-and-plan.md` §2 六条原则、§3.2、§5 第 7–10 条、§6 Phase 1。
- 脚手架已就绪：`packages/engine`（`src/index.ts` 占位）、`packages/policy-data`（`schemas/`、`fixtures/` 空目录）。`pnpm lint / typecheck / test / build` 当前全过。
- 政策依据：`docs/SOURCES.md` 的 SRC-001（官方回应 PDF，`policy-sources/`），本机可用 `pdftotext -layout` 抽文本。`docs/pending-details.md` 与 `docs/transitional-arrangements.md` 若已存在则参考，不存在则以 plan §3.2 为准。

## 设计决定（已定，不要重开）

- 规则 = TypeScript 函数 + 元数据对象，不做 DSL。
- 数据与 fixtures 用 TypeScript 模块，类型即 schema：不引入 ajv / zod / JSON Schema，不写运行时校验。`packages/policy-data/schemas/` 目录改为存放共享类型的说明或直接删除，二选一。
- 参数化：任何政策数字只出现在 `packages/policy-data` 的参数模块里，并带 `SourceRef`；规则代码通过参数名引用。
- MVP-0 范围：Skilled Worker 现行 5 年路径、Earned Settlement 3/5/10/20 年收入计数、public funds 基础分支、过渡安排判断、路线组切换重置、高风险短路。类型只为这些服务，不为 Phase 2+ 预留字段（需要时用注释标 `Phase 2`，不写字段）。

## 要做的

1. `packages/engine/src/types.ts`（可拆成少量文件，不要一类型一文件）
   - 输入 `PersonTimeline`：出生日期、国籍；`ImmigrationEpisode[]`（route、validFrom、validTo、role main / dependant）；`Absence[]`；`IncomeYear[]`（taxYear、earnings）；`BenefitEpisode[]`（benefitType、from、to）；`Relationship[]`（partner / parent / child，对方身份 British citizen / settled / other）；`EnglishEvidence`（CEFR 等级或豁免）；`CriminalEvent[]`、`ImmigrationBreach[]`、`GovernmentDebt`：只需能触发短路的粗粒度字段，不建模细节。
   - `SimulationRequest { timeline, simulationDate, ruleSetIds? }`。
   - `RuleSet { id, kind: 'LAW' | 'ANNOUNCED', status: 'CURRENT_LAW' | 'ANNOUNCED_NOT_IN_FORCE' | 'IN_FORCE_FUTURE_VERSION', effectiveFrom?, effectiveTo?, supersedes?, sources: SourceRef[] }`。
   - `RuleMeta { id, ruleSetId, title, sources: SourceRef[], pendingDetails: string[] }`（`pendingDetails` 放 `PD-xxx` 编号）；规则本体签名 `(ctx: RuleContext) => RuleResult`，`RuleResult` 为 `PASS | FAIL | UNKNOWN` 加说明与引用。
   - `SourceRef { srcId: string; locator: string }`，例如 `{ srcId: 'SRC-001', locator: 'p16' }`。
   - 输出：`DecisionOutcome` 六态（plan §2 第 5 条）；`SettlementAssessment { outcome, routeGroup, pathwayYears?, earliestDate?, satisfied: RuleId[], failed: RuleId[], unknown: RuleId[], assumptions: string[], sources: SourceRef[] }`；`SimulationResult { policyAsOf, byRuleSet: Record<RuleSetId, SettlementAssessment>, shortCircuit?: { reason, message } }`。
   - `Route` 枚举与 `RouteGroup` 分类（core permission / high talent / british connection / not counting / outside framework / protection），严格按 SRC-001 p18、p23–p26 建表，放在 `packages/policy-data/src/routes.ts`，每组带 `SourceRef`。MVP-0 之外的路线只需枚举名与分组，不需其他字段；留一个 `OTHER`。
2. `packages/policy-data/src/parameters/earned-settlement-2026-11.ts`：`ParameterSet { ruleSetId, values }`，至少含 £12,571、£50,271、£125,141、£25,142 与各自的 best-years 窗口（3 of 4、3 of 5、5 of 7）、public funds 回看 5 年、20 年路径；每个值带 `SourceRef`（SRC-001 p15–p18、p46）。再加现行 Skilled Worker 的 £41,700 参数，来源 `{ srcId: 'SRC-004', locator: 'SW 4.2' }`（settlement 对应 SW 24.3 row A）；再加 settlement 英语 B2 的申请日分界 2027-03-26（SRC-004 SW 22A.1；SRC-007），作为"带日期条件的参数"示例。
3. 两个示例 fixture（`packages/policy-data/fixtures/*.ts`，导出 `Fixture { id, title, source: SourceRef, request: SimulationRequest, expected: { outcome, pathwayYears?, earliestDate?, mustFail?: RuleId[], mustUnknown?: RuleId[] } }`）：官方 Individual C（合并收入，p19）与 Individual D（public funds，p19），`expected` 按原文；`fixtures/index.ts` 导出数组。
4. `packages/engine/src/evaluate.ts`：`evaluate(request): SimulationResult` 的签名与 stub（返回 `INSUFFICIENT_INFORMATION`，`policyAsOf` 取参数集日期）；一个测试：遍历所有 fixture，`evaluate(fixture.request)` 返回合法形状。真正的预期断言留给 Phase 1（用 `test.todo` 标出）。
5. `docs/contracts.md`：1–2 页说明类型之间的关系、规则为什么是 TS 函数 + 元数据、fixture 怎么写、参数怎么引用、规则必须带来源；给 astra 和 sol 看。
